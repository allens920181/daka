# 02 · 品牌

## 2.1 名稱

**RollRoom**，中英文都一樣。

`RollRoom` ＝ roll call ＋ room。room 說的是這個產品的形狀：一個有代碼、可以邀請人進來、事情做完就散掉的暫時空間。英文介面從頭到尾用 room，中文介面用「空間」講同一件事；兩邊為什麼不一樣，見 §2.1.1。

**兩種語言共用同一個名字。** 中文版一度叫「誰沒到」。收斂成單一名稱的理由是維護面：兩個名字表示 README、manifest、i18n、文件標題各要顧兩套，而口頭傳播還會多一道「誰沒到就是 RollRoom」的翻譯。

**代價要講清楚**，因為它跟 §2.3 的「零學習成本」有張力：中文使用者第一眼看到的是一個英文字。撐住這個決定的是首頁副標——**名字底下那一行必須用中文把產品講完**，目前是「大家一起點同一份名單」。名字可以是英文，第二行不行。

考慮過但沒採用：

| 候選 | 沒採用的理由 |
| --- | --- |
| 誰沒到（曾經的中文名） | 直接說出產品回答的那個問題，是個好名字；但維護兩套名稱的成本，加上口頭傳播的那道翻譯，比它換來的親切感貴 |
| Roll Call／點名房間（舊名） | 是品類描述不是名字，跟商店裡的「點名易」「TAKO 點名」擠在同一格 |
| Muster | 英文語意最準（集合並清點人數），但同名的點名與消防集合系統一大票，而且正好落在下面「不是企業軟體」那一格 |
| WhosHere／Whoo 等 Who- 開頭 | 這個命名空間被交友與定位社交 App 佔滿。更關鍵的是台灣有 Whoscall，而本產品的最後一個動作正是撥號給沒到的人，會被整個吃掉 |
| WhoRoom | 唸出來是 "whore-oom" |
| 還有誰／少了誰 | 當年評估中文名時的另外兩個候選：一個少了場景會被聽成「還有誰要報名」，一個語氣太重像現場出事了 |

### 2.1.1 單位名稱：中文「空間」，英文 room

主揪「創建空間」，協助者「加入空間」，六碼的那組字串叫「代碼」。

**中文不用「房間」，因為「開」會接上「房」。**「開房」「開一間房」在台灣是旅館的意思——首頁副標一度就寫成「開一間房，大家一起點同一份名單」。改成「空間」之後這個碰撞整個消失，動詞可以自由用「開一個」「開啟」而不必繞路。

**英文不跟著改，繼續用 room。** 英文的 room 沒有這個問題（hotel room 要講出 hotel），而且產品名 `RollRoom` 就建立在它上面。兩邊的單位名稱不一致是刻意的：碰撞是中文獨有的，只在中文修就好。

**「房號」一起換成「代碼」。**「空號」在中文是空號碼的意思，不能用。而「代碼」有個額外的好處：它不綁單位名稱，之後單位名稱再改一次也不必動它。

「空間」仍然精準描述這個產品的形狀——**一個有代碼、可以邀請人進來、事情做完就散掉的暫時場所**。它跟「房間」一樣是從視訊會議與遊戲借來的詞，中年志工也懂。

**兩個陷阱：**

- **不要寫「還沒有空間」**——會被讀成硬碟沒空間。首頁空狀態寫的是「還沒有開過空間」。
- **量詞用「個」不用「間」。** 「開一個」、「這個空間」、「還沒有開過空間」。

考慮過但沒採用：

| 候選 | 沒採用的理由 |
| --- | --- |
| 房間 | 原本用的詞，意象最好，但「開房」「開一間房」在台灣是旅館的意思 |
| 點名板 | 意象好（取代紙板），但「加入點名板」讀起來不自然 |
| 場次 / 活動 | 太正式，而且跟「活動」的日常語意打架 |
| 群組 | 會被誤解成長期存在的東西，但空間是一次性的 |

**要改名稱怎麼做：**名字散在七處，中英文同一個字串，改就是七處一起改：

| 位置 | 說明 |
| --- | --- |
| `src/lib/i18n.ts` 的 `appName`（zh／en 各一筆，值相同） | 首頁大標與分享標題 |
| `index.html` 的 `<title>` | 分頁名稱、書籤、分享預覽 |
| `index.html` 的 `apple-mobile-web-app-title` | iOS 加到主畫面的標籤 |
| `vite.config.ts` manifest 的 `name`／`short_name` | Android／PWA 安裝後的名稱 |
| `package.json` 的 `name`、README 與這份設計系統的標題、`src/styles.css` 檔頭 | 專案身分，不影響畫面 |

前四類在 bundle 內外各半，i18n 管不到後面那些——漏掉任何一處，使用者就會在分頁標題或主畫面圖示上看到舊名字。

單位名稱是另一件事：中文的「空間」與「代碼」共 32 處字串，同樣都在 `src/lib/i18n.ts`；英文的 room 不動。元件裡不得寫死中文，所以這兩種改名都只動一個檔，不必翻程式碼。**程式裡的識別字（`openRoom`、`roomCode`、`Room.tsx`）跟著英文，不跟著中文改。**

## 2.2 一句話

> 三十秒開一場點名，五個人同時點，馬上知道誰還沒到。

這句話決定了首頁該長什麼樣：一份可以篩選「所有／我的／他人的」的空間清單，篩選鍵下面跟著這個分類該做的那個動作——「我的」置頂「創建空間」，「他人的」置頂「加入空間」（按了開一張面板，代碼與掃碼都在裡面，平常不佔位置），「所有」兩顆都在——其他什麼都不要。

**但篩選只在有兩個以上的空間時才出現**（2026-09）。它本來永遠都在，於是**第一次
打開這個 app 的人，看到的第一個東西是一組為空清單準備的三段篩選器**——一條 56px
的控制項，比它底下那顆「創建空間」還早被讀到，而它在那個當下一件事都做不到。
門檻放在「兩個以上」而不是「一個以上」：一個空間不需要篩選。收起來時篩選一定
停在「所有」（沒有人改得動它），所以兩顆按鈕都在——那正是空手起步時該有的畫面。

## 2.3 品牌個性

五個特徵，每一個都對應到具體的設計決定。**沒有對應設計決定的形容詞不准寫進來**——那是廣告詞不是規範。

> **2026-09 更正。**「體貼」那一格原本寫的是「逆光下有觸覺回饋」。**全專案沒有
> 任何一處 `navigator.vibrate`，而且補上也沒有用：iOS Safari 不支援 Vibration
> API，加到主畫面的 PWA 一樣不支援。** 這條規則（形容詞要對應設計決定）本來就
> 是為了擋住這種句子，而它擋住的前提是那個對應**真的存在**——「有觸覺回饋」看
> 起來像一個具體的設計決定，所以沒有人回頭查。
>
> 逆光下的第二條確認管道其實一直都在，只是寫錯了名字：**那顆實心綠勾與 Toast**。
> 一個是形狀（不靠顏色，色覺差異也認得），一個是文字（寫著誰被標成已到，而且
> 可以復原）。那是真的，而且做得不錯。見 [iOS 評估](../design-review-2026-09-ios.md) §3.1。

| 特徵 | 對應的設計決定 |
| --- | --- |
| **可靠** | 離線可用、狀態誠實、不快取 API 回應、結果帶得走 |
| **直白** | 寫「還有 4 位沒到」不寫「pending: 4」；錯誤訊息一定含「怎麼辦」 |
| **快** | 零延遲回饋、不載入網路字型、大觸控目標、零學習成本 |
| **體貼** | 每次變更都能復原、破壞性動作要確認、點完的回饋有兩條路（實心綠勾＋Toast），逆光下也認得出來 |
| **不搶戲** | 沒有慶祝動畫、沒有得意的空狀態插圖。使用時人的注意力應該在排隊的人身上 |

## 2.4 這個品牌不是什麼

反面比正面更能擋住錯誤的提案。

**不是企業軟體。** 沒有 dashboard 美學、沒有用資料密度炫技、沒有一次塞五個 KPI。畫面上只有一個大數字。

**不是消費級社交 App。** 全部到齊時不放彩帶動畫、不放 emoji、不做連續打卡天數之類的遊戲化。點完名的正確反應是把手機收起來。

**不是宗教視覺。** 沒有十字架、鴿子、聖光漸層。這一點值得特別寫下來：這個工具是為教會做的，但**同一份需求在學校、公司員旅、社團集合完全一樣**。一旦戴上宗教符號，就把其他使用者擋在門外，也讓教會自己在對外活動時不好用。服務教會，不代表要長得像教會。

**不是「設計感」的展示。** 不用會擋住首次渲染的網路字型，不用在爛網路上載不完的插圖。視覺獨特性的優先度低於「早上七點打得開」。

## 2.5 標誌

一份清單：兩項已勾、一項未勾。

**未勾的那一項是重點**——這個產品存在的理由不是「已經到了幾個」，是「還有誰沒到」。標誌畫的就是那個還沒被勾起來的格子。

| 規格 | 值 |
| --- | --- |
| 構成網格 | 512 × 512，圓角 112（22%） |
| 底色 | `#0E5E63`（品牌 teal，固定不隨主題變） |
| 前景 | 白，未勾項 50% 不透明 |
| 內容範圍 | x/y 92–420 |
| 最小尺寸 | 24px。再小就把未勾的那一項拿掉，只留兩個勾 |
| 留白 | 四周至少一個勾選格的高度 |
| 原始檔 | `public/favicon.svg` |

**maskable 一定要另外一張圖。** 上面這張是 `rx=112` 的圓角徽章，四個角是透明的
——那正是 maskable 不能用它的原因：作業系統會自己套形狀遮罩（圓形、方角、
水滴…），拿圓角圖去餵就變成「圓角再被圓角切一次」，或在彩色底上露出透明的
四個角。

| 規格 | 值 |
| --- | --- |
| 構成 | 512 × 512，**無圓角、滿版底色**，四角不透明 |
| 內容 | 同一組圖形置中縮到 92%，半對角線 195px < 安全區半徑 205px（中央 80%） |
| 原始檔 | `public/icon-maskable-512.svg` |

**不得：**改底色、加陰影或漸層、把圖示放在其他形狀裡、拉伸比例、在標誌旁加標語。

### 2.5.1 Google 登入按鈕（第三方品牌，具名例外）

`.btn-google` 與 `IconGoogle` **不屬於這個設計系統**，它們照 Google 自己的
Sign-in with Google 按鈕規範走。這是整份規範裡唯一允許的第三方樣式例外。

| | 淺色 | 深色 |
| --- | --- | --- |
| `--google-bg` | `#ffffff` | `#131314` |
| `--google-ink` | `#1f1f1f`（16.5:1） | `#e3e3e3`（14.5:1） |
| `--google-line` | `#747775`（4.5:1） | `#8e918f`（5.8:1） |

**為什麼不用 `.btn-primary`：** Google 的標記必須維持原色，而四色的 G 放在品牌
teal 上既違反他們的規範，藍色與綠色的對比也不夠。深色時按鈕底只比面板亮
**1.07:1**，跟 Toast 一樣靠邊框定義形狀。

**`IconGoogle` 是全系統唯一不用 `currentColor` 的圖示**，也只出現在這一顆按鈕上。

**這四個 token 不參與這個系統的任何配色決定，不得用在別的地方。**

## 2.6 色彩的由來

| 色 | 為什麼是它 |
| --- | --- |
| **Teal `#0E5E63`** | 需要一個「可靠的系統色」。不用藍（企業感太重、也太常見），不用紫（消費 App 的預設）。深 teal 帶點工業感，像調度台或安全設備，跟「現場清點」的世界對得上 |
| **金琥珀 `#ab6900`** | 「未到」的顏色。**它要說的是「還有事情要做」，不是「出事了」**——所以是金、是黃銅、是計數器上的數字，不是施工三角錐 |
| **綠 `#407443`** | 「已到」。這是唯一該讓人放鬆的顏色，所以只給這一個狀態用；而且它刻意不彩——已到的人不需要任何行動 |
| **石墨藍灰階（254°、彩度 .008–.023）** | 灰階要「選過」，但**既不能往品牌色偏，也不能往紫偏**。這一行 2026-09 改過兩次，理由見下 |

紅色（`--fb-error`）**只給失敗與破壞性動作**，不參與點名狀態。名單上沒有「壞掉」的人。

### 2.6.1 「未到」不是警告（2026-09 配色重構）

這一輪動的是整套顏色，但只有一個判斷是真正的品牌判斷：

> **這個產品最正常的狀態，不該穿警告色。**

舊的「未到」是燒赭 `#a84d06`（OKLCH L53 / H49°），而 `--fb-error` 是 L47 / H29°
——**只差 20° 色相、6 點亮度**；`--fb-warn` 更直接，它跟「未到」是**同一個十六
進位值**。於是：一場點名開場時 100% 的人都未到，畫面上那個數字亮著跟「加入失敗」
一樣的顏色，然後隨著大家上車慢慢冷靜下來。**這個 app 是焦慮的，而它不該是。**

「未到 N」是這個產品要回答的那個問題的答案，是**工作量**不是**故障**。
移到 H68° 的金琥珀之後，它離失敗紅有 43°，讀起來是計數、是黃銅、是還沒劃掉的
項目——需要你動手，但沒有人出事。

品牌個性表（§2.3）裡的「不搶戲」與「體貼」，在這一條之前只落實在動畫與文案上；
配色一直在說相反的話。

### 2.6.2 灰階改過兩次，第二次是修方向（2026-09 配色重構）

**第一版：往品牌色偏。** 理由寫的是「純中性灰讀起來像沒選過」。那個直覺沒錯，
錯的是方向——它偏的是 teal 自己的色相（`--paper` 200°），而**背景已經是那個
色相，強調色就沒有東西可以推**。

**第二版：移到「~240°」。** 方向對了，但**那個數字是在 HSL 裡挑的**。換算到感知
空間（OKLCH）之後落點是 **286°**——不是冷中性灰，是**薰衣草紫灰**。中明度的
`--ink-2` `#55555f`、`--rule-strong` `#8e8e9a` 帶著看得見的藕紫調，而紫正好在
暖琥珀的補色方向上：「未到 N」不是在中性背景上自然亮起來，是被推成一個對立面。
整個 app 讀起來冷、硬、像實驗室——而使用者是早上七點站在停車場的志工。

**第三版（現在）：254°，真正的藍調石墨。** 離 teal 52°、離金琥珀 174°，
彩度低到 .008–.023：仍然是選過的灰，但在任何一階上都不會被讀成「有顏色」。

> **量色相要用感知空間量。** 240° 的目標與 286° 的落點差了 46°——一整個色相
> 家族，而那個誤差在規範裡被寫成一句自信的「彩度 2–3%」躺了整整一輪。
> HSL 的色相不是等感知的，藍紫區間尤其會騙人。

### 2.6.3 品牌 teal 一個位元都沒動

不是捨不得改：`#0E5E63` 在 L44 已經是 **sRGB 在該亮度能給的彩度上限的 ~95%**。
teal 是整個色相環上 sRGB 最擠的方向（L60 的天花板 C.102，同亮度的紅是 .242）
——**「它看起來像板岩不像 teal」不是它的錯，而且也修不了**：調更彩會出色域，
調亮就配不住白字。

壓住它的是周圍：紫灰背景，加上 `--accent-soft` 淡到 C.015（那個「teal 淡底」
其實是灰的）。淡底提到 C.032、背景換成石墨之後，同一個 `#0E5E63` 終於讀得出來
是品牌色。

**favicon、maskable icon、manifest、theme-color（淺色）都沒有改。**
已經把 app 加到主畫面的人，圖示不會在某天早上換色。

## 2.7 字型立場

**不載入任何網路字型**，一律用系統字級聯。

這是品牌決定，不只是技術決定：這個工具的承諾是「早上七點在訊號差的停車場打得開」。字型檔會擋住首次渲染，為了視覺獨特性犧牲那個承諾，就是把品牌個性排序反了。

系統字級聯（`src/styles.css`）：
```
-apple-system, BlinkMacSystemFont, 'Segoe UI', Roboto,
'Noto Sans TC', 'PingFang TC', 'Microsoft JhengHei', 'Helvetica Neue', sans-serif
```

等寬（代碼、電話、時間、數字）：
```
ui-monospace, SFMono-Regular, 'SF Mono', Menlo, Consolas, monospace
```

> 例外：`docs/` 底下對外的說明頁可以用網路字型，那些頁面沒有現場使用的限制。

| 資產 | 規格 | 位置 |

| Favicon | SVG，512 viewBox | `public/favicon.svg` |
| PWA 圖示 | 192 × 192 PNG | `public/icon-192.png` |
| PWA 圖示 | 512 × 512 PNG，`purpose: any` | `public/icon-512.png` |
| PWA maskable 圖示 | 512 × 512 PNG，滿版無圓角 | `public/icon-maskable-512.png` |
| Apple touch icon | 指向 icon-192 | `index.html` |
| theme-color | 淺色 `#0e5e63`（品牌 teal，未改）／深色 `#0b0f13`，兩個 meta 各帶 media | `index.html` |
| App 名稱 | `RollRoom`／短名同為 `RollRoom`，中英文一致 | `vite.config.ts` manifest、`index.html` |
| iOS 狀態列 | `apple-mobile-web-app-status-bar-style: default`（**不要改**，見下） | `index.html` |

**iOS 狀態列一律 `default`，不得改成 `black-translucent`**（2026-09，[iOS 評估](../design-review-2026-09-ios.md) §3.3）。

`black-translucent` 會讓頂欄延伸到狀態列底下，看起來比較滿版——這也是為什麼
下一個人會想改它。**但它同時強制狀態列文字變成白色**，而這個 app 的淺色模式是
接近白的 `--paper`：白字白底，時間與電量在淺色模式下直接看不見。

深色模式看起來會很好，所以**在深色模式下測不出這個問題**。這是它值得寫下來的
原因：一個只在一半情況下壞掉的改動，比全壞的更容易被放行。

（`viewport-fit=cover` 是另一件事，它照舊——安全區的讓開由 `env(safe-area-inset-*)`
負責，頂欄與底部動作列都已經接了。）

**改圖示時要一起改的**：`favicon.svg` 是來源，`icon-192/512.png` 由它產生；
`icon-maskable-512.svg`（滿版版本）另外維護，`icon-maskable-512.png` 由它產生。
只改 SVG 不重新產 PNG，桌面圖示就會跟瀏覽器分頁不一致。

## 2.9 QR 碼

QR **一律白底黑碼**，即使在深色模式。

掃描器要的是對比，不是配色。把 QR 做成品牌色或深色底是很常見的錯誤，代價是有人在昏暗的教會門口掃不進去。

QR 卡片（`.qr-card`）是整個系統裡唯一允許寫死 `#fff` 的地方，這條例外寫在 `src/styles.test.ts` 裡。
