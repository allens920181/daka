# 01 · 基礎

## 1.1 設計前提

所有規則都從這五個現場條件推導出來。看到不合理的規則，先回來看是不是漏了某個前提。

| 前提 | 對設計的意義 |
| --- | --- |
| **單手、站著、人潮在動** | 觸控目標要大、主要動作在拇指可及範圍、位置不能跳動 |
| **戶外、可能逆光** | 對比不能將就；狀態不能只靠顏色；觸覺是第二個確認管道 |
| **訊號差或沒訊號** | 不得有任何操作要等網路才給回應；離線狀態必須一直看得見 |
| **使用者是志工，不是員工** | 零學習成本，不能有需要訓練才會用的互動 |
| **一次性、不能重來** | 可逆動作要能復原；不可逆動作要明確確認；要有紙本備援 |

這五條不是價值觀宣言，是**可以推翻規則的事實**。如果哪天這個工具改成給室內、坐著、有 Wi-Fi 的櫃台人員用，整套規範都該重寫。

## 1.2 五條原則

依重要性排序。衝突時，排前面的贏。

### 1. 未到優先

畫面上最大的數字永遠是「還有幾位沒到」。已到的人視覺上要退到背景。

*為什麼：* 使用者要的不是「已經來了幾個」，是「還要等誰、要打給誰」。已到的人不需要任何行動。

*具體約束：* 未到人數要一直看得見——它長在頂欄的篩選那排（「未到 N」），頂欄是 sticky，所以捲到名單多深它都在。這個數字不能消失。

### 2. 本地優先

任何操作都在 100ms 內從本地狀態給出結果。網路狀態另外顯示，不阻擋操作。

*為什麼：* 停車場收訊差、轉圈圈兩秒，同工就會連點三下，然後開始不信任這個工具。

*具體約束：* 點名不得有 loading 狀態。網路請求一律非同步，逾時 12 秒。離線時操作照常，只是同步指示改變。

### 3. 可逆優先

每一次狀態變更都提供 5 秒的無條件復原。不可逆的動作要有確認對話框。

*為什麼：* 誤觸的代價是有人被留在原地。

*具體約束：* 復原按鈕不得低調化（它是安全機制，不是次要動作）。確認對話框的初始焦點放在「取消」。

### 4. 位置穩定

動作按鈕不隨狀態改變位置或順序。

*為什麼：* 在壓力下操作的人靠位置記憶，不靠閱讀。

*具體約束：* 篩選（未到／已到／請假）住在頂欄裡，永遠在同一個位置，不隨捲動、
不隨狀態消失。「請假」段只在有人請假時出現且永遠在最後。搜尋框固定在頂欄裡、
一直顯示，不必先點開才找得到，位置與可見性都永遠不變。

*槽位裝什麼：* 頂欄的篩選段本身就是「未到 N」——不再需要另一個地方重複這個
數字。收尾要做的「複製結果」移進管理面板第一項，一場活動按一次的東西不需要
永久佔位。

> **這一條在 2026-08 修正過一次，2026-09 整段換掉一次，同月稍後又補了第三次。**
>
> **2026-08**：原本槽位裝的是「分享」與「臨時加人」，理由寫的是「即使全部
> 到齊也不變」——也就是把「位置穩定」讀成了「內容也不准改」。那是誤讀：
> **位置穩定保護的是「同一個東西永遠在同一個地方」，不是「一開始選錯的東西
> 不准換掉」。** 而且原本的選擇本身就不對：五支手機裡有四支是掃 QR 進來的
> 協助者，他們永遠不需要分享，卻整場都被那顆按鈕佔著最好的拇指位置；反過來，
> 收尾時真正要按的「只看未到」在畫面最上方，而那時你已經捲過 80 個人。分享
> 退回頂欄那顆已經存在的 48px 圖示鍵，臨時加人移進管理面板。
>
> **2026-09**：底部動作列（`.dock`）整條拿掉，連同它保護的「兩個固定槽位」
> 一起。導火線是攜伴不再從貼上的文字裡解析（見 §6.5 的修正）之後，計分區的
> 大字與「未到 N」變成同一件事，計分區跟著整塊拿掉，篩選搬進了 sticky 頂欄。
> 這時「只看未到」的存在理由消失了——它切換的那個狀態，頂欄的篩選段本來就
> 一直顯示著，兩者變成同一個功能佔兩個位置。留在底部列的「複製結果」是
> 一場活動只按一次的動作，不值得永久佔用一列人名的高度，移進管理面板第一項。
> 剩下唯一整場反覆使用的是搜尋，而它原本在頂欄右上角——390×844 上單手要跨
> 780px 才按得到。搬成浮在右下角的鍵（.fab），才是這個原則真正該保護的東西：
> 拇指反覆要按的那一顆固定在拇指能到的地方，不是「固定兩個槽位」這個形式
> 本身。
>
> **2026-09（同月第三次）**：浮動搜尋鍵（.fab）也拿掉了，搜尋框直接一直
> 開在頂欄裡，不必先點才展開。.fab 解決的是「按不按得到」，但沒解決「要
> 先按一下」這件事本身——搜尋是整場反覆在用的動作，多一步「點開」跟多一段
> 780px 的距離一樣，都是重複成本，只是前者量不出 px。輸入框原本就因為要
> 避開 iOS 鍵盤蓋住底部元素而放在頂欄；頂欄本身一直是 sticky、一直在畫面
> 上，讓框永遠開著並不會多佔什麼，只是把「按得到」直接換成「不必按」。
> 這次不是又換了一個槽位裝的東西，是把「反覆要按的動作固定在拇指到得了的
> 地方」這個道理往前推一步：能不必按，就不要留一顆鍵。

### 5. 誠實

離線就說離線，不要假裝已同步。不確定就說不確定。

*為什麼：* 這個工具唯一的價值是「數字是對的」。一次假裝同步就毀掉全部信任。

*具體約束：* 不快取 API 回應。同步狀態四種各有明確文字。單機模式要主動說「其他人看不到」。

*這條原則最容易在四個地方破掉，各有具體規則：*

1. **會做出承諾的畫面必須讀 `connection`。** 首頁掛一句「單機模式」不算數——
   真正做出「別人加得進來」這個承諾的是分享面板，那裡才是必須說話的地方。
   單機模式下分享面板不發代碼、不產 QR、不給連結，改成講清楚別人會看到什麼。
2. **失敗訊息不得承諾沒有發生的事。** 「恢復連線後會自動上傳」只有在東西真的
   進了待送佇列時才能說。開空間、進空間、改名單、寄驗證碼失敗時什麼都沒入列，
   要說的是「這個動作沒有完成」。真的會自動上傳的只有點名，而那件事由同步
   指示負責說。若要說「你貼的東西還留著」，就得先真的存下來
   （`storage.ts` 的 `saveDraft`）。
3. **同一種錯誤在不同地方後果不同，就得講不同的話。** 「連不上網路」在開空間是
   「空間沒開成」，在進空間是「載不下來」，在單機模式下輸入別人的代碼則根本不是
   網路問題（`errorMessage(e, t, where)`）。共用一句話一定會有一個地方在說謊。
4. **被伺服器拒絕的操作要當面說，不能靜靜丟掉。** 本地優先代表使用者已經看到
   自己的操作成功了；佇列裡那一筆被永久拒絕時如果無聲移除，同步指示接著會翻成
   綠色的「已同步」，然後畫面自己彈回舊值。訊息裡必須有人名，並接著重新對帳
   讓畫面回到伺服器的真相。

## 1.3 這些原則之間怎麼取捨

| 衝突 | 怎麼判 |
| --- | --- |
| 未到優先 vs 位置穩定 | 位置穩定贏。搜尋鍵不因為未到人數變化而移位或消失，即使那個位置在某些狀態下不是最省力的 |
| 本地優先 vs 誠實 | 兩者兼顧：本地立刻更新畫面，同時明確顯示「N 筆待上傳」 |
| 可逆優先 vs 快 | 可逆優先贏。多一個 Toast 的視覺成本，換一次不會有人被丟包 |
