# 08 · 貢獻

---

## 8.1 加一個新元件

1. **先確認它真的是新元件。** 多數「需要新元件」其實是既有元件被用在不該用的地方。翻一遍 [04 元件](04-components/) 的「不要用在」欄。
2. 在對應的家族檔案裡，用[規格模板](04-components/README.md#規格模板)寫下規格——**先寫規格再寫程式**。寫不出「不要用在」通常代表這個元件的用途還沒想清楚。
3. 實作。只用 token，不寫死任何數值。
4. 補齊全部狀態：預設 / hover / 按下 / 焦點 / 停用。缺哪個要在規格裡說明為什麼。
5. 補無障礙契約：role、aria、鍵盤、焦點。
6. 跑 `npm test`、`npm run audit:design`、`npm run e2e`。
7. 如果這個元件有行為契約（焦點、Esc、復原），在 `scripts/e2e-local.mjs` 加一條斷言。

---

## 8.2 改一個 token

改 token 會影響所有用到它的地方，這是好事——但要先確認影響範圍。

1. `grep -rn "\-\-token-name" src/` 看誰在用。
2. 改 `src/styles.css` 的**三處**：`:root`、`@media (prefers-color-scheme: dark)`、`:root[data-theme='dark']`。
   漏掉任何一處，`src/styles.test.ts` 會抓到。
3. 如果是顏色，先算對比。`scripts/design-audit.mjs` 會驗，但事前算比事後修快。
4. 更新 [03 Token](03-tokens.md) 的表格，包含新的對比數字。
5. 全套檢查。

**新增一階**（例如第九個字級）要先問：是真的缺一階，還是有個地方用錯階？
八階字級是從 17 種收斂來的，加回去很容易，收斂很難。

## 8.3 何時可以違反規範

可以，但要留下痕跡。

**可以違反的情況**

- 使用者明確要求，而規範跟需求衝突。→ 照做，並更新規範說明這個例外。
- 規範沒涵蓋到的新情境。→ 先做，然後補進規範。
- 外部限制（例如 QR 必須白底）。→ 在規範裡寫成**具名例外**，並在檢查腳本裡加白名單。

**不可以違反的情況**

- 「這樣比較好看」。
- 「這次先這樣，之後再改」。
- 沒有人會發現。

**留痕跡的方式**：例外一律寫進規範文件與檢查腳本，不要只寫在程式碼註解裡。
註解會被讀，但不會被執行；白名單會被執行。

## 8.4 檢查清單

送出改動之前：

```
[ ] npm test              token 靜態檢查 + 單元測試
[ ] npm run build         型別檢查 + 建置
[ ] npm run audit:design  設計規範（需要先 preview）
[ ] npm run e2e           元件行為（需要先 preview）
[ ] 手動檢查              見 07 品質 §7.5
[ ] 規範文件是否需要跟著更新？
```

完整指令見 [README](../../README.md#開發)。

---

## 8.5 這份規範自己的維護

- 規範與程式碼**放在同一個 repo、同一個 commit**。規格與實作分開放，一定會漂移。
- 改實作時如果規範沒跟著改，就是規範壞了，不是實作壞了。
- 視覺對照頁是**衍生物**，不是來源。以 markdown 為準。
- 這份規範描述的是**現在的系統**，不是理想的系統。還沒做的東西寫在 [README 的已知限制](../../README.md#已知限制)，不要寫成規範——規範裡的每一條都應該是可以立刻驗證的。

---

## 8.6 還沒進入規範的東西

以下功能在路線圖上但尚未實作，所以**刻意不寫規格**——等真的做的時候，現場會告訴我們該長什麼樣：

- 分車／分組（資料庫已有 `group_label` 欄位）
- 看板模式（平板大字顯示）
- 常用名單跨裝置
- 主揪帳號（協助者維持匿名）

寫規格描述不存在的元件，只會產生一份沒人驗證過的猜測。
