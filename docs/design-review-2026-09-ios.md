# 設計評估報告 · 2026-09 · 以 iOS 為標竿

> 前幾份報告是拿這個專案自己的規範對帳。**這一份換一把尺：Apple HIG。**

「以 iOS 為標竿」不是把它做得看起來像 iOS App。這是一個裝在 iPhone 上、
**以 PWA 形式加到主畫面**的工具，而它的使用者一天用 iOS 用了十幾個小時——
所以標竿的意思是：

> **iOS 使用者已經有的期待，就是這個 app 的規格。**
> 他們期待字會跟著系統的文字大小變、期待從左緣右滑會回上一頁、期待頂欄底下
> 有東西在動。這些不是風格偏好，是他們不用學就會的東西。

以下每一條都附實測數字（iPhone 邏輯尺寸 390×844）。

---

## 0. 先講對的：這些已經是 iOS 水準

先校準，免得下面的清單讀起來像全盤否定。

| 項目 | 現況 | HIG |
| --- | --- | --- |

| 分段控制 | 凹槽軌道 ＋ 浮起的選中格 | 幾乎就是 `UISegmentedControl` ✓ |
| 破壞性確認 | 置中對話框、初始焦點在「取消」 | ✓ 就是 iOS alert 的做法 |
| 面板握把 | 頂端置中的膠囊 | ✓ 就是 iOS 的 grabber |
| 列尾的 `›` | 灰色、靠右 | ✓ 就是 disclosure indicator |
| 深色模式 | 完整兩套色票 | ✓ |
| 減少動態 | `prefers-reduced-motion` 全關 | ✓ |
| 輸入框 17px | 避開 iOS 自動放大 | ✓ 這一條很多 web app 都沒做 |

**這個 app 的底子是好的。** 下面的問題集中在兩個地方：**平台整合**（系統設定與

## 1. 要做（會實際咬到使用者）

### 1.1 完全不支援 Dynamic Type

**現況：** 七階字級全部是 `px`；`-webkit-text-size-adjust` 是 `auto`（預設值，
**不等於 Dynamic Type**）。

```
--fs-1: 11px  --fs-2: 13px  --fs-3: 15px  --fs-4: 17px
--fs-5: 20px  --fs-6: 26px  --fs-7: 34px
```

**iOS：** HIG 把「支援 Dynamic Type」列為基本要求。使用者在
「設定 › 螢幕顯示與亮度 › 文字大小」或「輔助使用 › 更大的文字」調過之後，
**期待每一個 app 都跟著變**。

**對這個產品的代價特別大**，因為它自己的前提就寫著：

> 使用者是志工，不是員工 ／ 戶外、可能逆光

一個把系統字調到特大的中年志工，打開這個 app 看到的還是 13px 的備註與
15px 的說明。**他在別的 app 都看得到，只有這個看不到。**

**怎麼做：**

```css
html { font: -apple-system-body; }   /* iOS 上這一行會跟著 Dynamic Type 走 */
:root {
  --fs-1: 0.6875rem;  /* 11/16 */
  --fs-2: 0.8125rem;  /* 13/16 */
  ...
}
```

`-apple-system-body` 是 WebKit 支援的字型簡寫關鍵字，它會把 root font-size
綁到使用者的 Dynamic Type 設定；非 iOS 平台落回 16px，所有 `rem` 值不變。

**要一起檢查的：**

- **觸控尺寸維持 px。** `--tap-min` / `--tap-row` / `--tap-lg` 是**物理尺寸**，
  跟字級無關，不得換成 rem。
- 名單列的 `min-height: 64px` 已經是 `min-height`，字變大時列會自己長高 ✓
- `.member-note` 的兩行封頂（`-webkit-line-clamp: 2`）在特大字下要重看。
- 「輸入框不得低於 16px」這條在 rem 之後仍然成立（17/16 rem ≥ 1rem）。
- `scripts/design-audit.mjs` 的七階檢查要改成比對 rem 換算後的值，
  並且**加跑一輪放大字級的情境**。

**這是這份報告裡最大的一條。** 它是唯一一個「iOS 使用者會發現這個 app 壞掉」
的問題——其他每一條都只是「不夠好」。

#### 已實作（2026-09）

做出來的樣子跟上面的草稿有兩處不同，都是實測之後改的：

**一、分母是 17，不是 16。**

```css
--fs-1: calc(11 / 17 * 1rem);   /* 而不是 0.6875rem */
```

分子就是那一階原本的 px 值，讀的人不用回頭換算，也不會有四捨五入的漂移。
搭配根字級的 17 基準，**預設狀態下七階算出來還是 11/13/15/17/20/26/34，
一個像素都沒有變**——這次改的是「使用者調過字級之後會發生什麼事」，
不是畫面現在長什麼樣。

**二、根字級不能寫死成 `17px`。**

草稿只講了 Apple 那一半。寫死 px 的版本在 Apple 平台是對的（`font` 簡寫會覆蓋
掉它），但在**其他平台就把使用者調過的預設字級吃掉了**——Android Chrome 與桌面
瀏覽器都有同一個設定，而這一行會壓過它。那正是這一條要修的問題本身，只是換了
一個平台發生。

```css
:root {
  font-size: calc(17 / 16 * 1rem);   /* 跟著瀏覽器設定的預設字級走 */
  font: -apple-system-body;          /* Apple 平台改綁 Dynamic Type */
}
```

根元素上的 `rem` 指的是 font-size 的**初始值**（＝使用者設的預設字級），所以
第一行是「他的預設字級 × 17/16」：沒動過就是 17px，把 Chrome 調到 24px 就是
25.5px。實測確認兩邊都成立。

**清單上其餘四項的結果：**

- 觸控三個 token 維持 px ✓（`--tap-*` 那一段加了「不得改成 rem」的註記）
- 名單列會自己長高 ✓（1.5 倍字級下實測 66 → 90px，備註照樣兩行封頂、不重疊）
- 輸入框 ≥ 16px ✓，而且字級只會被往上調，這條在放大情境下更安全
- 檢查工具兩邊都補上了 ↓

**留下來的一個固定高度。** `.code-row` / `.code-input` 的 `height: --tap-lg`
是寫死的（當初是為了跟旁邊那顆鍵對齊），字放大之後框不會跟著長：瀏覽器預設
字級 32px 時那裡的字是 52px，關在 54px 的框裡。改成 `min-height` 之後兩件事
都成立——預設仍然剛好 56px（實測），撐不下時框跟著長高。**任何有文字的固定
高度都是同一個問題**，這條寫進了 `docs/design/03-tokens.md` §3.2。

**檢查工具：**

- `src/styles.test.ts` 的「沒有硬寫的 font-size」改成放行**整組機制**而不是某個
  數值：根字級那兩行必須成對出現，少了 `-apple-system-body`（Apple 端失效）或
  把第一行寫回 px（其他平台失效）都會被抓出來。三種回歸各驗過一次。
- `scripts/design-audit.mjs` 的七階檢查改成先用當下的根字級反算回「第幾階」，
  並加跑第三輪：把瀏覽器預設字級調到 24px（內文 17 → 25.5px，大約落在 iOS
  Dynamic Type 的 xxxLarge 與 AX1 之間）。那一輪也會先對一次根字級——CDP 沒吃到
  設定的話，這輪會安靜地退化成「再跑一次淺色」，照樣通過但什麼都沒驗到。
  三輪全過。
- 同時補了一個新檢查：**文字被自己的框夾住**。寫死高度的容器在放大字級下會把
  字切掉，而原本每一項檢查都看不到——對比達標、觸控尺寸夠大、字級在七階內、
  頁面也沒有橫向溢出。`.code-row` 那組固定高度就是被它抓出來的（第一版寫在
  「有文字節點」的分支裡，對著已知的 bug 跑出來是「通過」：input 的值不是文字
  節點，而寫死高度的框十之八九就是輸入框）。

### 1.2 系統返回手勢完全沒接上

**現況：** `useModal` 裡沒有 `pushState`，全專案只有一處 `history.replaceState`
（OAuth 回來時清網址）。面板、面板的子畫面、編輯模式**全部只是元件狀態**。

**後果（iOS 上會實際發生）：**

| 使用者做的事 | 他預期 | 實際發生 |
| --- | --- | --- |
| 在「更多」面板上從左緣右滑 | 關掉面板 | **整個退出空間**，回到首頁 |
| 在「邀請點名 › 代碼」右滑 | 回到「邀請點名」 | 同上，直接離開空間 |
| 在設定的「主題」子畫面右滑 | 回到設定清單 | 離開首頁（可能退出 app） |

邊緣右滑在 iOS 上是**主要的返回操作**，在 standalone PWA 裡更是如此——那裡
沒有瀏覽器的返回鍵，右滑是唯一的。

**這同時是這個專案自己的原則被打破：**「位置穩定」說的是使用者靠位置記憶操作，
而這裡是使用者靠**肌肉記憶**操作，結果被送到完全不同的地方。

**怎麼做：** 開面板時 `history.pushState`，`popstate` 對應到關閉／返回上一頁；
面板的 `setMode` 換頁同樣各推一格。改動集中在 `useModal.ts` 與各張 Sheet 的
`setMode`，行為契約（Esc、返回鍵、點遮罩）都不變，只是多一條入口。

**順帶解掉 Android 實體返回鍵**——現在按下去也是直接離開空間。

### 1.3 名單是 N 張浮起的卡片，iOS 是一張卡片＋髮絲線

**實測（390×844，40 人）：**

| | |
| --- | --- |
| 列高 | 66px |
| 列與列的間距 | 8px |
| 每人佔用 | **74px** |
| 首屏看得到 | **9 個人** |
| 頂欄到第一個名字 | 125px（螢幕高的 15%；有分車時約 200px） |
| 40 人的間距總和 | **312px ＝ 4.2 列人名** |

**iOS：** inset grouped list——**一張圓角卡片**裝所有列，列與列之間是
**髮絲分隔線**（1px 或 0.5px），而且分隔線**從文字的起點開始**（縮排讓開前導
圖示），不是整條貫穿。沒有每列自己的陰影與邊框。

**先誠實講一件事：首屏不會多看到人。** 可用高度 655px ÷ 74 = 8.8（9 人），
÷ 66 = 9.9（還是 9 人）。**收掉間距換到的不是首屏密度**，是這兩件：

1. **80 人的名單少捲 632px** ——大約 8.5 列人名的距離。
2. **視覺噪點少一個數量級**：現在是 8 個陰影 ＋ 8 圈邊框 ＋ 7 道間隙；
   iOS 的做法是 1 圈邊框 ＋ 7 條髮絲線。

**但這一條有真的取捨，所以列為「要決定方向」而不是「照做」：**

現在的設計用**高度**編碼狀態——未到浮起（`--surface` ＋ `--el-1`）、已到沉回
頁面。那是這個 app 目前最好的一個決定（原則一：已到的人要退到背景）。
**收進一張卡片之後，「浮起」這個管道就沒有了。**

三個可能的方向：

| 方向 | 狀態怎麼表達 | 代價 |
| --- | --- | --- |
| **A. 維持現狀** | 浮起／沉回 | 捲動距離與噪點照舊 |
| **B. 完全 iOS** | 只剩勾 ＋ 文字降階 | 失去最強的那個管道；「已到退到背景」變弱 |
| **C. 分段卡片**（建議） | **未到**的連續段落收進一張卡片＋髮絲線；**已到**的列退出卡片、直接坐在頁面上 | 名單被狀態切成幾段，捲動時段落會重排——需要實測會不會讓人點錯 |

C 是把 iOS 的容器語言拿來替原則一服務：**卡片＝還要處理的那一群**。
它保留「浮起／沉回」的語意（現在是整段浮起），又拿到髮絲線的密度。
**但它是三個裡面唯一沒有前例的，要先做一版來看。**

#### 已實作：C，但中途改了一次（2026-09）

做出來的樣子成立，讀起來就是那句話——一段連續的未到是一張卡片，已到的列坐在
頁面上。分車標題自然切斷一段（`+` 選不過去），那本來就是兩群人。

**「要先做一版來看」看到的東西不是版面，是一個量出來才會知道的 bug。**

上面那張表把 C 的代價寫成「捲動時段落會重排——需要實測會不會讓人點錯」。實測
的結果比那句話具體，而且更糟：

| 動作 | 下面的人往下跑 |
| --- | --- |
| 點掉一段裡的一個人 | 8px |
| 點掉一段中間的人（把一段切成兩段） | 16px |
| **由上往下點六個** | **48px** |

**是累積的。** 第一版只收未到與未到之間的縫，所以每點掉一個人，那一列就從段落
裡退出來、多開兩道 8px 的縫。40 人的名單點完，還沒點到的人被往下推超過 300px
——**點名這個動作本身把待辦的人一直推離手指**。而
「位置不能跳動」是這個專案的[第一條現場前提](design/01-foundations.md)，
它保護的正是「單手、站著、人潮在動」的那個人。

改法：**間距一律收掉，不分狀態**（`.member + .member` 一律 `-8px`）。每個人固定
佔 66px，點誰都不會動到任何人的位置（實測漂移 0px）。間距本來就不是在區分這兩
群人的東西——區分它們的是表面（卡片 vs 頁面）與那條髮絲線，而那兩樣**不佔高度**。
順帶把密度也拿滿了：74px → 66px，比原本估的還多省一點。

e2e 加了 4 個檢查，其中兩個就是為了擋這個 bug 回來（固定節距、點四個人之後第
10 個人漂移 ≤ 1px）。把間距規則改回第一版，那條檢查會說「漂移 32px」。

**回頭看，這一條的價值不在選對了方向，在於那句「不能紙上決定」。** A、B、C 三個
方向紙上都看不出這件事——它不在版面裡，在**版面隨著使用而改變的方式**裡。

## 2. 值得做（成本低、很有感）

### 2.1 頂欄與底部動作列不是半透明材質

**現況：** 兩者都是 `--paper` 實色，`backdrop-filter: none`。

**iOS：** nav bar 與 toolbar 是 translucent material——底下的內容會透出來並被
模糊。那不只是好看：**它讓人知道底下還有東西、而且正在動。**

```css
.topbar, .dock {
  background: color-mix(in srgb, var(--paper) 72%, transparent);
  backdrop-filter: saturate(180%) blur(20px);
}
@supports not (backdrop-filter: blur(1px)) {
  .topbar, .dock { background: var(--paper); }
}
@media (prefers-reduced-transparency: reduce) {
  .topbar, .dock { background: var(--paper); backdrop-filter: none; }
}
```

**要驗的：** `design-audit.mjs` 量對比時取的是 `backgroundColor`，半透明底會讓
它算錯——那份腳本的 `bgOf()` 是往上找第一個 `alpha > 0.5` 的祖先，72% 剛好在
門檻上，**要先確認它取到的是合成後的顏色**，不然這個改動會讓對比檢查失真。

#### 已實作（2026-09）

CSS 照上面那份寫，兩處不同：

- `@supports` 要**兩個寫法一起測**。Safari 18 之前只認 `-webkit-backdrop-filter`，
  只測沒有前綴的版本會讓 iOS 15–17 判成「不支援」而退回實色——正好是我們想給它
  的那群人。條件寫成
  `not ((backdrop-filter: blur(1px)) or (-webkit-backdrop-filter: blur(1px)))`。
- 兩個屬性都寫（前綴的在前）。

**上面那段「要驗的」猜對了方向，但猜錯了原因。** 實際去量才發現：`color-mix()`
算出來的顏色，Chromium 回的是 `color(srgb 0.96 0.97 0.98 / 0.72)`——而
`parse()` 的 regex 只認 `rgb()／rgba()`，對它回 `null`。於是 `bgOf()` 把整個
半透明層當成「根本沒有底色」跳過去，**材質等於沒有被量到，檢查照樣說通過**。

門檻猜錯至少還會算出一個錯的數字；連字串都沒認得，是連錯的數字都沒有。兩件事
一起修了：

- `parse()` 加上 `color(srgb …)`（分量 0–1，要 ×255）。修完實測：舊解析器對頂欄
  的底色回 `null`，新的回 `246/248/250 @ 0.72`，正是 `--paper` 的 `#f6f8fa`。
- `bgOf()` 不再用「第一個 alpha > 0.5」那個猜的門檻，改成**真的往下疊**：一層層
  收集半透明的底，碰到不透明的那一層（或 body）就停，再由下往上合成回來。

**還是量不到的一件事**（寫在腳本的註解裡）：`backdrop-filter` 吃的是**畫面上**
在它後面的東西，不是 DOM 裡的祖先。頂欄底下捲過去的名單卡片不在那條祖先鏈上，
所以算出來的是「沒有東西捲到底下時」的顏色——靜止狀態的正確答案，不是全部的
答案。按鈕不受影響（`.btn` 自己有 `--surface` 實底），受影響的是頂欄標題，
它確實直接坐在材質上，iOS 的 nav bar 標題也是。

`prefers-reduced-transparency: reduce` 用 CDP 模擬驗過：兩條退路都回到
`rgb(246, 248, 250)` 實色、`backdrop-filter: none`。三輪檢查全過。

### 2.2 面板呈現時底層不縮

**iOS：** 從 iOS 13 起，sheet 會把底下的畫面縮小（約 0.92）、加圓角、往下推一點。
那個動作在說「你還在那一頁，只是暫時蓋住了」。

**現況：** 只蓋一層 `--scrim`。

純視覺，但它是 iOS sheet 最有辨識度的一個動作。改動量小（一個 transform 在
`#app` 上，配合 `data-modal`），而且 `prefers-reduced-motion` 已經有全域關閉。

### 2.3 缺 `enterkeyhint`

代碼輸入的 iOS 鍵盤屬性做得很好（`autocapitalize="characters"`、
`autocomplete="off"`、`spellcheck={false}`），但其他輸入框沒有 `enterkeyhint`：

| 欄位 | 建議 |
| --- | --- |
| `#room-name` | `enterkeyhint="next"` |
| `#checker-name` | `enterkeyhint="done"` |
| 六碼代碼 / 驗證碼 | `enterkeyhint="go"` |
| Email | `enterkeyhint="next"`（已有 `type="email"` ✓） |

iOS 會把 return 鍵換成對應的字。一行一個屬性。

#### 已實作（2026-09）

**不只是一行一個屬性。** 鍵上寫「前往」按下去卻什麼都沒發生，比一顆普通的
return 鍵更糟——它承諾過。所以每一個都補上了對應的行為：

| 欄位 | `enterkeyhint` | 按下去真的發生的事 |
| --- | --- | --- |
| 首頁代碼框 | `go` | 加入空間（本來就有） |
| `#room-name` | `next` | 焦點跳到名單欄（新接） |
| `#checker-name` | `done` | 存起來、回上一頁（新接） |
| 登入 Email | `send` | 寄出驗證碼（本來就有） |
| 六碼驗證碼 | `go` | 驗證並登入（本來就有） |
| 名單搜尋 | `done` | 收鍵盤，字與框都留著（新接） |

兩處跟原本的建議不同：

- **Email 是 `send` 不是 `next`。** 按下去寄的是驗證碼，不是跳到下一欄——
  下一欄要等信到了才存在。
- **多了名單搜尋這一欄。** 結果是邊打邊出來的，所以 return 鍵只剩一件事可做：
  把鍵盤收掉。這在 iOS 上不是小事——不接的話，收鍵盤的唯一辦法是點別的地方，
  而這個畫面上「別的地方」就是名單列，**點下去會直接把人標成已到**。

`#roster-text` 刻意沒有：它是多行的，那顆鍵該換行就是換行。
e2e 加了 5 個檢查，驗的是那個承諾（按下去發生了什麼），不只是屬性有沒有寫上去。

### 2.4 面板圓角 18px，iOS 約 10pt

小事，但 18px 在 iPhone 上明顯比系統面板圓。若要對齊，`--r-3` 從 18 → 12–14。
**注意這會動到 `.dialog`**，而 iOS alert 的圓角是 14pt——所以 14 兩邊都對得上。

## 3. 平台事實：規範宣稱了 iOS 做不到的事

### 3.1 「逆光下有觸覺回饋」是假的

`docs/design/02-brand.md` 的品牌個性表寫著：

> **體貼** | 每次變更都能復原、破壞性動作要確認、**逆光下有觸覺回饋**

**全專案沒有任何一處 `navigator.vibrate`。** 而且就算補上也沒有用——
**iOS Safari 不支援 Vibration API**，standalone PWA 一樣不支援。

這是這個專案第五次出現「散文描述著不存在的東西」，而這一次特別值得記：
**它宣稱的是一個平台層級的能力，而那個平台不給。**

**行動：** 把那一格改寫成實際成立的東西。逆光下的第二確認管道現在其實是
**Toast ＋ 那顆實心綠勾**，那是真的、而且做得不錯——規範應該寫那個。

#### 已實作（2026-09）

改了**兩個**地方，不是一個。品牌表那一格是果，因在更上游：

- `docs/design/01-foundations.md` 的五條現場前提，「戶外、可能逆光」那一條寫著
  **「觸覺是第二個確認管道」**。前提寫著一個平台不給的能力，從它推導出來的規則
  就會落在空的地方——品牌表那一格正是這樣長出來的。改成「每個動作要有第二個
  確認管道」，並註明實際在做這件事的是形狀與文字。
- `docs/design/02-brand.md` 的品牌個性表改寫，兩處都留下更正說明。

`docs/design/04-components/overlays.md` 那一段不用改：它記的是「震動回饋整個功能
被拿掉了」，本來就是準確的歷史。**這正好說明這條錯誤是怎麼活下來的**——功能刪
了、刪除紀錄寫了，但兩份上游文件裡的那句話沒有人回頭改。

那張表自己的規則是「沒有對應設計決定的形容詞不准寫進來」。它擋不住這一句，是
因為「有觸覺回饋」**看起來就像一個具體的設計決定**——規則擋得住廣告詞，擋不住
一個曾經為真的句子。

### 3.2 iOS 會在 7 天後清掉單機模式的名單

**現況：** 名單、待送佇列、常用名單全部存在 IndexedDB（`idb-keyval`）。

**iOS：** Safari 的 ITP 對「script-writable storage」有**七天無互動即清除**的
政策。`navigator.storage.persist()` 在 iOS Safari **不支援**，所以 app 沒有辦法
主動要求豁免。加到主畫面的 standalone PWA 有自己的儲存區、實務上不受這條影響。

**這個產品正好踩在情境上：** 產品方向書把「回程用複製空間」列為核心情境，
而一場活動與回程之間可能隔兩週。單機模式的使用者兩週後打開，**名單不見了**。

**行動（三件，都不難）：**

1. 首頁那句單機模式提示要說出後果，現在只說「其他人看不到」。
2. iOS Safari 且非 standalone 時，明確引導「加到主畫面」——那是唯一真正的解法。
3. 收尾時的 CSV／複製已經有了，但它們現在的定位是「帶去別的地方」，
   在單機模式下它們其實是**唯一的備份**。文案要反映這件事。

### 3.3 `apple-mobile-web-app-status-bar-style: default` 是對的，但沒寫下為什麼

現況 `default` ＋ `viewport-fit=cover`。想要 iOS 那種頂欄延伸到狀態列底下的
滿版感要用 `black-translucent`——**但那會強制白色狀態列文字**，淺色模式下就
看不見了。

所以 `default` 是正確的選擇。**問題只是規範沒寫，下一個人會想「改成
translucent 比較潮」然後在淺色模式下踩到。** 補一段進 `02-brand.md §2.8`。

## 5. 這一輪學到的

### 5.1 換一把尺，會量到自己那把尺量不到的東西

前四份報告把這個專案自己的規範對帳到很細——顏色進了 OKLCH、形狀有了兩條軸、
元件合併了、箭頭收成兩個方向。**但那四份沒有一份問過「系統的文字大小設定
會不會生效」或「右滑會發生什麼」**，因為專案自己的規範裡沒有這兩條。

**規範只驗得到它自己寫過的東西。** 定期換一把外部的尺，量到的是規範的**邊界**
在哪裡，而不是規範內部的不一致。

### 5.2 平台整合的缺陷不會出現在截圖裡

這一輪最重的兩條——Dynamic Type 與返回手勢——**在任何一張截圖上都看不出來**。
前四輪的方法（把六個畫面並排看）對它們完全無效，必須去讀程式碼、查平台政策。

**看得出來的問題會被修，看不出來的會活很久。**

### 5.3 不要宣稱平台不給的能力

「逆光下有觸覺回饋」寫在品牌個性表裡，而 iOS 根本沒有 Vibration API。
規範寫承諾之前要先問：**這個承諾在我們最大的平台上兌現得了嗎？**
