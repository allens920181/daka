# 五支手機，一份名單 — 產品方向與架構

> 現在的 `index.html` 假設「一個人、一支手機」。真正的場景是**五個同工站在遊覽車門口，同時點同一份名單**。
> 這一句話決定了接下來所有的技術選擇——而它不是加功能能解決的，是資料要換地方存。

**定位一句話：三十秒開一場點名，五個人同時點，馬上知道誰還沒到。**

---

## 一、現況盤點

### 該保留的

零安裝、貼上名單就能用、離線也能跑、介面乾淨。尤其「不用註冊就能開始」——對一群不想裝 App 的教會同工來說，這是能不能推動起來的關鍵。任何改版都不能弄丟這四件事。

### 現場會咬人的五個問題

| 位置 | 問題 | 後果 |
| --- | --- | --- |
| `index.html:588` `:847` | 打卡狀態用姓名字串當 key（`checkedInNames[name]`） | 兩個「陳怡君」＝點一個、兩個都變已到，另一個被留在原地 |
| `index.html:760` | 按「載入名單」直接 `checkedInNames = {}`，無確認無備份 | 點到第 60 個人時手滑，80 人重來 |
| `index.html:836` | 整張卡片都是感應區，且沒有 undo | 誤觸把「未到」變「已到」＝那個人不會被打電話，車就開走了 |
| `index.html:919` | `getCurrentTime()` 只回傳 `HH:MM:SS` | 沒有日期就分不出哪一天，也做不出回程點名 |
| `index.html:614` `:668` | `currentLang` 先被設成存檔值，才呼叫 `switchLanguage(currentLang)`，而函式開頭的 `if (lang === currentLang) return` 讓它每次都直接跳出 | 選了 English 重整回來還是中文 |

另外 `renderNameList()` 每點一下就把整份名單 `innerHTML = ''` 重建一次（`:772`）——80 人還撐得住，200 人在舊手機上會開始頓，畫面也會跳。

---

## 二、真正的斷點

上面五個都是可以修的 bug。但就算全修完，這個工具在這個場景裡還是會壞掉，因為 `localStorage` 存的是**單一瀏覽器的私有資料**。五個同工打開同一個網址，就是五份互不相干的名單。

現場會長這樣：A 點了王小明，B 不知道又點一次；C 以為 D 會顧後門，兩邊都沒點到三個人；最後主揪問「到底幾個人上車了」，五支手機給出五個答案。

> **核心不是「現代化」，是把名單從『一支手機的記憶』搬到『一場活動的共同記憶』。**
> UI 再漂亮、程式再模組化，只要這件事沒做，現場還是會出事。

## 三、把出遊那天走一遍

需求不該從功能清單長出來，該從現場長出來。

| 時間 | 現場發生什麼 | 推導出的需求 |
| --- | --- | --- |
| 前一天晚上 | 主揪把 LINE 報名接龍貼進去，開一場「秋季旅遊 · 出發」 | **貼上解析要夠寬容**：`1.王小明`、`2. 李美花 +1`、`3、陳大同（請假）` 都要吃得下 |
| 當天 06:50 | 五位同工掃 QR，同時進到同一份名單。沒有註冊、登入、安裝 | **加入必須零摩擦**：一組活動代碼 ＋ 一張 QR。這是產品能不能被真的用起來的分水嶺 |
| 07:00–07:12 | 人潮上車，五個人各點各的，數字一起跳。有人重複點到同一個 | **即時同步 ＋ 冪等**：重複點名不能重複計算；點下去要立刻有反應，不能等網路 |
| 07:12 | 停車場收訊差，一支手機轉圈圈。同工照點不誤，收訊回來自動補上 | **離線是預設假設，不是加分項** |
| 07:15 | 主揪切到「未到」剩三人，直接點名字撥號 | **「誰還沒到」才是主畫面**，要能 `tel:` 撥號、一鍵複製成文字貼回 LINE |
| 07:20 | 車開了 | **結束要有明確動作**：封存這一輪、留下可匯出的結果 |
| 16:40 休息站 | 回程集合。開「回程」這一輪，**同一份名單、重新歸零**，再點一次 | **一場活動要能點很多輪**——這是最被低估的需求。把人留在休息站，就是這個產品存在的理由 |

## 四、把邊界劃清楚

| 是這個 | 不是這個 |
| --- | --- |
| 單次活動的現場清點 | 員工差勤／薪資勾稽 |
| 多人同時點同一份名單 | 教友會員資料庫 |
| 掃碼即用，不用帳號 | 長期出席率報表（至少不是現在） |
| 訊號差也要能運作 | 權限與組織階層管理 |
| 結束後知道誰沒到、能立刻聯絡 | GPS／人臉／NFC 驗證打卡 |

## 五、架構決策一：名單要放在哪裡

這是唯一真正困難的決定，其他都是它的下游。

| 方案 | 多人同步 | 離線 | 費用 | 建置成本 | 主要風險 |
| --- | --- | --- | --- | --- | --- |
| 純本地 `localStorage`（現況） | 做不到 | 天生就有 | 零 | 零 | 五份名單對不起來——就是現在的問題 |
| 點對點 WebRTC / PeerJS | 勉強 | 部分 | 近乎零（仍需 STUN/TURN） | 高 | 行動網路 NAT 穿透常失敗，五人 mesh 更脆弱。**偏偏訊號差正是最需要它運作的時候** |
| **Supabase（Postgres + Realtime）** | **內建** | **需自建佇列** | **免費方案夠用** | **中** | **免費專案閒置一段時間會暫停** |
| Cloudflare Workers + Durable Objects | 內建 | 需自建佇列 | 極低 | 中高 | 技術上最漂亮（一場活動＝一個 DO 房間，閒置休眠不計費），但要多養一套部署流程 |
| Firebase Realtime Database | 內建 | SDK 內建 | 免費方案夠用 | 中 | 離線支援最省事，但與 Google 生態綁得較深 |

> 各家免費方案的額度與規則會變動，請以官網當下條款為準。這裡比較的是*形狀*，不是數字。

### 建議：Supabase

1. **它同時解決同步與儲存。** Postgres 存名單、Realtime 推播變更，一套服務、一組金鑰，不用自己維護 WebSocket 伺服器。
2. **匿名存取模型剛好對得上。** 用 anon key ＋ RLS，把讀寫權限綁在「活動代碼」上，就能做到「掃碼即用、不用註冊」——這正是場景的生命線。
3. **它不會擋住之後想做的事。** 常用名單庫、歷史紀錄、出席統計本來就是 SQL 擅長的；用 Cloudflare DO 這些都要自己再長一套。

**要正視的代價：** 免費專案閒置過久會被暫停，而「一個月一次出遊」這種間歇型使用正好會踩到。解法是用 GitHub Actions 排一個每週 cron 打一次極輕量查詢把它叫醒。這是已知問題與已知對策，但要知道它存在——**不要出遊當天早上七點才發現連不上**。

如果之後覺得 Supabase 太重，**Cloudflare Durable Objects 是最好的第二選擇**：「一場活動＝一個房間物件」在語意上比資料表更貼合這個場景，也沒有閒置暫停問題。它輸在生態系與學習成本，不是輸在技術。

## 六、架構決策二：點下去那一刻發生什麼事

接了後端最容易犯的錯，是讓「點名」去等網路回應。停車場收訊差、轉圈圈兩秒，同工就會連點三下，然後開始不信任這個工具。

所以寫入路徑必須是**本地優先**：

```
手機 A（點名員）
┌────────────────────┐
│   畫面             │
│    ↕ 即時讀寫       │   ──待送佇列──→   雲端活動室   ──即時廣播──→   手機 B
│   本地狀態          │    離線時堆著      code: K7F2QM                 手機 C
│   (IndexedDB)      │    連線再送
└────────────────────┘
```

畫面永遠只讀寫本地狀態，所以點下去是零延遲的；網路只負責把待送佇列裡的變更推上去、再廣播回來。斷線時左半段照常運作，佇列堆著等連線。

### 五個人同時改，誰贏？

一般講到多人協作就會想到 CRDT（Yjs、Automerge）。**這個場景不需要。** 這個領域的操作幾乎是單調的——人上了車就不會下車，衝突罕見，而且每個人的狀態只是一個小小的列舉值，不是一份會被同時編輯的文件。

用「**每人一筆、後寫者勝**」（last-write-wins）就夠了，只要每筆變更帶一個單調遞增的時戳（混合邏輯時鐘，避免手機時間不準造成亂序）。規則一句話講得完、出事時看資料就知道為什麼，比引入一整套 CRDT 執行期好維護太多。

真的會撞的只有一種：A 剛點「已到」、B 同時按「取消」。**後者勝，並且要讓兩個人都看見有人改過**——顯示「07:03 由 陳姐 標記為未到」比默默覆蓋安全得多。

## 七、資料模型

```
Event                                   // 一場活動
  id · code:"K7F2QM" · name:"秋季旅遊" · createdAt · expiresAt
  │
  ├─ Member[]                           // 名單
  │     id:uuid · name · note? · companions:0 · group?:"1 車"
  │
  └─ Round[]                            // 點名回合：出發 / 回程 / 上午…
        id · name:"出發" · startedAt · closedAt?
        │
        └─ Record[]                     // 一人一筆，覆寫式
              memberId · status: 未到 | 已到 | 請假
              at:ISO8601 · by:"陳姐的手機" · rev:HLC
```

三個決定：

- **`Member.id` 是 uuid，不是姓名。** 兩個「陳怡君」從此各是各的。這一個改動就解掉現況最危險的 bug，而且*就算不接後端也該現在做*。
- **`Round` 是第一級概念，不是附屬品。** 一場活動可以點很多輪，同一份名單重新歸零。休息站的回程點名靠它。多數同類工具漏掉這件事。
- **`Record` 帶 `rev` 與 `by`。** 前者讓五支手機合併時有明確勝負規則，後者讓「誰改的」看得見——出事時這是唯一能還原現場的線索。

`Record` 是**每人一筆、就地覆寫**，不是事件流。資料量恆等於名單人數，同步與查詢都便宜，也不必寫壓縮邏輯。代價是失去逐筆歷史——對單次點名來說這個交換划算。

## 八、現場細節（不做就會被卡住）

- **寬容的貼上解析** — 自動去掉編號、全形空白與項目符號，把 `+1` 認成攜伴人數、括號認成備註。名單匯入是第一個接觸點，卡在這裡就沒有下一步。
- **臨時加人** — 沒報名但出現的人，要能當場一鍵加進名單。在教會活動裡是常態不是例外。
- **攜伴人數** — 「王媽媽 +2 個孫子」建議一列帶人數，因為要的是*總人數對得上*，不是每個孫子的名字。
- **分車／分組** — 兩三台遊覽車是常見的，每台車各看各的名單、各自算數。
- **「未到」是主畫面，不是篩選器** — 且要能直接 `tel:` 撥號、一鍵把「未到：張三、李四」複製成文字貼回 LINE。這是整個產品最有價值的三十秒。
- **防誤觸與 undo** — 感應區收斂成明確按鈕、每次變更留三秒「復原」提示。**誤觸的代價是有人被留在原地**，值得為它犧牲一點手速。
- **明確的連線狀態** — 「已同步 / 離線中，3 筆待上傳」要一直看得見。使用者可以接受離線，不能接受不知道自己在不在線上。
- **看板模式** — 一台平板放車門邊，大字顯示「已到 76 / 80」。

## 九、技術棧

**Vite ＋ TypeScript ＋ Preact ＋ Vitest ＋ PWA。**

Preact 打包後極小（行動網路上開得快），TypeScript 讓上面的資料模型變成編譯期就會擋錯的合約，Vite 讓 PWA 與 Service Worker 變成幾行設定。Vitest 用來測**解析器與合併規則**——這兩處最容易寫錯又最難用眼睛看出來。

**會改變的一件事：** 目前流程是「在 GitHub 網頁編輯 `index.html`，存檔就上線」。改成建置流程後，`index.html` 不再是原始碼，本機改程式要跑 `npm run dev`。

但**「推上 main 就自動部署」不會變**——GitHub Actions 從「上傳整個 repo」改成「先 build 再上傳 `dist/`」即可，依然可以完全不碰終端機。

## 十、路線圖

階段之間有一條刻意畫的線：**Phase 0 完全不碰後端，但資料模型先做對**。這樣 Phase 1 接同步時是「補上一層」，不是「重寫一遍」。

### Phase 0 — 把地基換掉（建議從這裡開始）

不接後端，單機就大幅變好用；而且之後不用白做一次。

- Event / Round / Member / Record 資料模型上線，`Member.id` 改用 uuid
- 寬容的名單貼上解析（編號、攜伴、備註）＋ 載入前確認，不再無聲清空
- 「未到」主畫面：撥號、複製成文字
- 防誤觸按鈕 ＋ undo ＋ 完整 ISO 時戳
- PWA：可安裝到桌面、離線可開；匯出 CSV／JSON
- 修掉語言設定失效、整份重繪等既有問題

### Phase 1 — 五個人看同一份名單（核心解鎖）

這一階段做完，這個工具才真的成立。

- 接上 Supabase：活動代碼、QR 加入、匿名存取 ＋ RLS
- 本地優先寫入 ＋ 待送佇列 ＋ Realtime 廣播
- 連線狀態指示、後寫者勝的合併規則、「誰改的」顯示
- GitHub Actions 每週 cron 保活

### Phase 2 — 現場強化

用過兩三次真實活動之後，才知道哪些真的重要。

- 分車／分組、攜伴人數、臨時加人
- 看板模式（平板大字顯示）
- 離線佇列的健壯化與衝突提示

### Phase 3 — 從「一次活動」長成「一個團體」

只有在前面都被穩定使用之後才值得做。

- 常用名單庫：小組／團契的固定名單，開活動時直接套用
- 歷史活動查詢、出席統計、月報匯出

## 十一、風險

### 名單是個資

一份教會成員的姓名與電話清單，拿到活動代碼的人就看得到。所以：代碼要夠長到猜不出來（六到八碼、排除易混淆字元）、**活動要會自動過期並刪除資料**（例如三十天）、管理動作（改名單、關閉活動、匯出）可以另外加一組只有主揪知道的 PIN。不必做到完整權限系統，但「過期自動刪除」建議直接寫進 Phase 1。

### Phase 0 的資料還是會不見

只要還在瀏覽器本機，清快取、換手機、無痕模式就等於資料消失。這是 Phase 0 的真實限制，要**誠實地讓使用者知道**——活動結束時主動提示匯出，而不是假裝它很安全。

### 出遊當天早上七點不能出事

使用時機極度集中且無法重來。所以離線必須是預設假設、免費方案的保活要排程，而且**活動前一天要能「預演」**——主揪自己掃一次 QR、確認名單載入正常。這種一次性、高風險的使用型態，比日常工具更需要一個明確的事前檢查動作。

---

## 十二、待決定

1. **先做 Phase 0，還是直接衝 Phase 1？** Phase 0 一兩天內就能給一個明顯好用很多的單機版；Phase 1 才真正解決痛點，但要多花時間也要開 Supabase 專案。建議 Phase 0 先做完並在一次真實活動用過，因為現場會教你 Phase 1 該長什麼樣。
2. **已經有 Supabase 帳號了嗎？** 沒有的話得先討論想不想維護一個雲端服務——這是從「一個 HTML 檔」變成「一個要顧的系統」的門檻。
3. **名單需要跨活動重複使用嗎？** 每次重貼，還是希望有「青年團契固定名單」可以直接套？這決定 Phase 3 是不是該提前。
4. **要記錄「誰點的」嗎？** 好處是能追溯，代價是加入時多一步選名字。傾向做成選填——不填就叫「點名員 2」。
5. **回程點名（多回合）真的是需求嗎？** 這是從「上遊覽車外出」推導出來的推測。如果實際上回程不點名，`Round` 可以簡化很多。
