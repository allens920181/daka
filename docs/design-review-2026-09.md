# 設計評估報告 · 2026-09 — 整體性

> 上一份（[2026-08](design-review-2026-08.md)）找的是 63 條可行動的問題。
> **這一份找的不是問題，是問題之間的關係。**

2026-09 一個月裡這個產品改了三十幾次，每一次都有道理，每一次的理由都寫在註解裡。
但把六個畫面並排看的時候，它不像一個產品：**顏色最重的地方不是最重要的地方，
每一塊東西都是同一種盒子，同一件事在不同畫面有不同長相，而規範裡有好幾段在
描述已經不存在的東西。**

這不是「迭代太多次」的錯。是每一次迭代問的都是「**這一塊**要不要留、好不好看」，
沒有人退開一步問「**眼睛第一個落在哪裡，那裡是不是最重要的東西**」。
局部最佳化三十次，會得到一個每一塊都合理、整體不成立的畫面。

---

## 1. 四個系統性問題

### 1.1 層級是反的

原則一（[01 基礎](design/01-foundations.md)）寫著兩句話：

> 畫面上最大的數字永遠是「還有幾位沒到」。**已到的人視覺上要退到背景。**

實作把兩句話都做反了：

| | 規範說 | 實際上 |
| --- | --- | --- |
| 未到人數 | 畫面上最大的數字 | `--fs-3`（15px）的**灰字**，跟旁邊兩個一樣重，比任何一個人名（20px）都小 |
| 已到的人 | 退到背景 | 整列鋪 `--st-arrived-soft`、鑲一圈綠邊 —— **全畫面最飽和的一塊顏色** |

而且 `--fs-8`（44px，token 表寫著「未到人數，每個畫面最多一個」）**一次都沒有被用過**。
它是為 2026-08 拿掉的計分區留的，計分區走了之後那句話就沒有實作了，沒有人發現，
因為刪計分區時只問了「它說的話有沒有別的地方在說」（有：篩選列的「未到 N」），
沒問「**它用多大的聲音在說，接手的地方有沒有一樣大聲**」。

結果就是 80 人的名單點到一半變成白綠相間的斑馬紋，眼睛被已經上車的人吸走，
而唯一要回答的那個數字縮在角落。

### 1.2 所有東西都是同一種盒子

首頁：灰盒子（單機模式）→ 灰盒子（三段篩選）→ 白盒子＋描邊（加入空間）→
實心盒子（創建空間）→ 白盒子（空間列）。點名畫面：灰軌道（篩選）→ 一排藥丸（分車）
→ 八個白盒子（人）。**每一個都是 12–18px 圓角、1px 邊框、差不多的視覺重量**，
於是它們之間沒有主從，只有先後。

規範裡其實已經有三次針對「框中框」「一疊盒子」的修正紀錄——但每一次都只拆掉當時
那一個框。沒有一條規則說「**什麼東西該有框，什麼東西不該有**」。

### 1.3 一個顏色喊五次

琥珀色（`--st-pending`）的語意是「未到」。畫面上同時有：篩選列的未到數、
「全部」晶片的數字、「第一車」的數字、「第二車」的數字⋯⋯**三台車就是四個琥珀
數字**，再加上綠色的已到列、teal 的選中晶片、teal 的辨識晶片。
一個顏色在同一屏喊五次，等於沒喊。

### 1.4 規範與實作各說各話

`src/design-docs.test.ts` 擋得住「規範提到一個不存在的 token」，擋不住散文。所以：

- `.sync` 的規格寫著「**不得**只用圓點顏色表達狀態，一定要附文字」——實作一個月前
  就只剩一顆圓點了。
- 分組晶片的規格寫著不變量是「各車相加 = 全部 = **大字**」——那個大字是 2026-08
  拿掉的計分區。
- 名單列的狀態表寫著已到用 `--st-arrived-soft`／`--st-arrived-line`。
- `--surface-3`（進度條底）、`--op-muted`、`--fs-8` 三個 token 沒有任何人在用。

## 2. 改了什麼

### 2.1 狀態改用**高度**表達，不用顏色

| 狀態 | 之前 | 現在 |
| --- | --- | --- |
| 未到 | 白底、1px 邊 | `--surface` ＋ `--el-1`：**浮在頁面上** |
| 已到 | 淡綠底、綠邊 | 透明（透出 `--paper`）、無陰影、文字降一階：**沉回頁面** |

那顆實心綠勾照舊，所以「顏色與形狀都要不同」沒有放鬆；退掉的只是那一整片底色。

三個附帶好處：眼睛落在還要處理的人身上；**深色模式不用另外配一組色票**
（「比頁面高一階」在明暗兩邊都成立，而 `#12291d` 那種深綠底是為深色另配的）；
省下來的顏色預算給了真正該喊的那個數字。

### 2.2 篩選列自己變成那個大數字

不把計分區裝回來（那要再吃掉一列人名），而是讓這一列**本來就在的那個數字**
長到該有的份量：`--fs-5`、700、`tabular-nums`，與標籤基線對齊。
**全畫面只有「未到」那一顆帶顏色**，選中與否都不變——選中是「你在看哪一群」，
跟「那一群有幾個人」是兩件事。

分組晶片的數字跟著改成中性（`--ink`、700），歸零才轉綠。一個顏色只喊一次。

`--fs-8` 隨之移除：八階字級收成七階。

### 2.3 一套表面規則

| 角色 | 用什麼 |
| --- | --- |
| 頁面 | `--paper` |
| 卡片／列／覆蓋層（面板、對話框） | `--surface` ＋ 邊框 ＋ 陰影 |
| 凹槽（分段軌道、提示框、預覽） | `--surface-2`，**不加邊框** |

按這條規則修掉的不一致：

- `.sheet` 的底色從 `--paper` 改成 `--surface`。面板與確認對話框是同一種東西，
  卻一個用頁面色、一個用卡片色；而且面板裡的凹槽（`--surface-2`）疊在 `--paper`
  上只差 1.06:1，凹不下去。
- `.empty` 的**虛線框拿掉**。那是全站唯一一處虛線、唯一一個用 `--r-3` 的非覆蓋層
  元件——一句「這裡什麼都沒有」長成畫面上視覺最特殊的一塊。
- `.banner-muted` 的**灰底拿掉**。`--surface-2` 疊在 `--paper` 上只差 1.08:1，
  那個填色沒有框住任何東西，只是在首頁最上面放了一塊三行高的灰方塊，比它底下的
  「創建空間」還早被讀到。有色底留給真的在說「這裡不一樣」的 warn／error。
- `.recent-item` 裡那條貫穿整列的 1px 界線拿掉。七列並排時那是七條短豎線在列隊，
  整份清單讀起來像一張表格。

### 2.4 排版缺陷

| 缺陷 | 修法 |
| --- | --- |
| 代碼輸入框 66px、旁邊的「加入」56px，並排的一列永遠是歪的 | 高度寫死 `--tap-lg`。**並排的元件要對齊，就不能讓其中一個的高度是字級的副產品** |
| 首頁把「這台裝置沒有雲端」說了兩次（頂端橫幅 ＋ 底部提示） | 留頂端那一條 |
| 第一次打開 app 看到的第一個東西是**為空清單準備的三段篩選器** | 兩個以上的空間才出現 |
| 選單裡「會開子畫面」和「當場做一件事」長得一模一樣 | 前者右邊加 `.go` 箭頭 |
| 結束對話框上四顆一樣重的按鈕排成兩列，像一組四選一 | 「複製／CSV」降成 `.btn-sm`；要做的決定只有底下那一個 |
| 解析預覽的備註晶片靠右，八列排下來右邊是一條鋸齒 | 跟在名字後面——它們是同一個人的兩件事 |
| 解析預覽的框撐到底，八個人的名單看起來像壞掉的十六個人 | 跟著內容長；要捲由面板自己捲 |
| `.chip-count` 與 `.chip-tell` 同色同形，分不出「帶幾個人」還是「哪一台車」 | 辨識晶片改藥丸形——**「屬於哪一群」在這個 app 裡一律是藥丸** |
| textarea 右下角一顆在手機上拉不動的原生拉桿 | `resize: none`（它已經自己長滿了） |
| `.member-side` 的 `border-left` 自從撥號鍵搬走就再也沒有被畫出來過 | 連同它的兩條覆寫規則一起刪 |

### 2.5 死掉的 token

`--fs-8`、`--op-muted`、`--surface-3`、`--st-arrived-soft`、`--st-arrived-line` 移除。
`--dur-3` 留著（規範裡明寫「保留」，那是刻意的）。

`--op-muted`（.62）值得單獨記一筆：它的用途本來就是「在場但不需要行動的東西」，
也就是已到的列——但**用 opacity 讓一整列退後會連文字對比一起壓掉**（實測 20px
的姓名降到 4.3:1，過不了 4.5）。要讓東西退後就明確換一階文字色，不要用透明度偷懶。

## 3. 沒有做的事

| 提過但沒做 | 理由 |
| --- | --- |
| 深色模式的主色調淡一點（`#3fbfc7` 是很亮的青） | 那組色票是照對比門檻調出來的，動它要重跑整條驗證鏈，而它不是「不一致」，只是「亮」。留給下一次專門處理色彩的評估 |
| 把分組晶片也收進分段控制的軌道語言 | 兩排控制項**該**長得不一樣：一排是切片（單位是列數），一排是答案（單位是人頭）。規範早就寫了這件事，是顏色在打架，不是形狀 |
| 首頁把篩選移到按鈕下面 | 那會拆掉「選了『我的』所以出現『創建空間』」這條因果。真正的問題是它在清單還空的時候就佔著最上面——那個問題用「兩個以上才出現」解掉了，不必動因果 |
| 名單列的密度（64px 列高） | 那是觸控尺寸的下限決定的，不是設計選擇 |

## 4. 怎麼避免再發生

這次四類問題有同一個根因：**沒有人定期把整個產品並排看一次。**

- **改一塊的時候，順手問第二個問題。** 不只「這一塊還有沒有人在用」，還有
  「它用多大的聲音在說，接手的地方有沒有一樣大聲」。1.1 整條就是漏了這一問。
- **刪東西要連著它的 token 一起刪。** 四個死 token 全部來自「功能拿掉了，色票留著」。
  留著的 token 會在下一次被誤用，或讓規範看起來還在描述一個存在的東西。
- **規範的散文也會漂移，而測試驗不到。** `src/design-docs.test.ts` 擋得住
  「提到一個不存在的 token」，擋不住「規格說一定要附文字，實作只剩一顆圓點」。
  所以改實作時要把對應那一段規格一起讀完——不是只搜 token 名字。
- **每隔一段時間，把六個畫面並排截圖看一次。** 這份報告的所有結論都來自那一步，
  而它花的時間比任何一次改動都短。
